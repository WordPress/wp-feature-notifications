# Core admin notice collector — alignment notes

## Summary

This plugin does not currently use an `admin_notices` collector. Its only `admin_notices` code was a single demo notice, removed with the 0.2.0 demo in #308 (`1de3a13`). The new core collector is, however, a clean foundation for issue #85 ("Demo Feedback: Move legacy notifications to hub"), which is still open.

## What landed in core

[wordpress-develop#13671](https://github.com/WordPress/wordpress-develop/pull/13671) was committed to trunk as r64282 (`1c277e1bbe`, "Admin: Admin notice accessibility improvements", Fixes [#50486](https://core.trac.wordpress.org/ticket/50486)), `@since 7.2.0`. The committed code is identical to the PR. The alternative approach, [#11923](https://github.com/WordPress/wordpress-develop/pull/11923), was closed at the same time.

- **`WP_Admin_Notice_Collector`** (`wp-includes/class-wp-admin-notice-collector.php`): a static class, initialised in `wp-admin/admin.php`. It hooks the `wp_admin_notice_markup` filter, so it only sees notices built through `wp_admin_notice()` / `wp_get_admin_notice()`. Raw markup echoed on `admin_notices` and JS-generated notices are not captured.
- **Public read API:** `get_notices()` returns `{ markup, message, args }` entries keyed by `args['notice_id']`. There are also `get_notice_count()` and `reset()`. Storage is in memory and lasts one request only.
- **Notice IDs:** `wp_get_admin_notice()` now adds `id` / `data-id` attributes like `wp-admin-notice-3`, generated by `wp_unique_prefixed_id()`. They are unique per request, not stable across requests.
- **Title count:** the admin `<title>` gets a prefix such as "(2 notices) " via an `admin_title` placeholder that an `ob_start()` callback resolves. Inline notices are included in the count.
- **JS** (`common.js` `moveAdminNotices()`): moves `div.notice`, `div.updated` and `div.error` (excluding `.inline` and `.below-h2`) into `<aside id="wp-admin-notices" aria-label="Admin Notices">` after `.wp-header-end` or the first heading. Where PHP renders the notices is unchanged.

## How we could align

### 1. Show page notices in the hub, read-only (recommended for #85)

On `admin_footer`, if `class_exists( 'WP_Admin_Notice_Collector' )`, read `WP_Admin_Notice_Collector::get_notices()` and pass the data to the `wp_notifications` script with `wp_add_inline_script()`.

The timing works:

- Notices print during `admin-header.php` (and inline in the page body), before the footer.
- Our script is enqueued in the footer, and `admin_footer` fires before footer scripts print.

The hub would show them in an "On this page" section, with this mapping:

| Collector | Hub `Notice` field |
|---|---|
| `args['type']` | `severity` |
| `args['dismissible']` | `dismissible` |
| `message` (via `wp_kses_post`) | `message` |

The notices still render in place, so this avoids the concern raised in #85 about re-rendering arbitrary notice HTML inside the hub. We mirror the message text only.

### 2. Things to handle in our code

- **Version guard:** our minimum is WordPress 6.7 and the collector exists from 7.2, so the feature needs the `class_exists` guard. On older versions the section is simply absent.
- **IDs:** `Notice.id` is typed as `number` (`src/types.ts`), but collector IDs are strings that change on every request. Page notices need their own type or ID namespace. For "seen" or dismiss state across page loads, use a stable key such as a hash of `type + message + args['id']`, not `notice_id`.
- **No DOM conflict:** our notices use `.wp-notification`, not `.notice`, so core's JS will not move them.
- **Landmarks:** there are now two `aside` landmarks on admin pages. `#wp-notifications-hub` contains an `h2` but has no accessible name; add `aria-labelledby` (or `aria-label`) so it is distinct from core's "Admin Notices" landmark.

### 3. Do not hide core notices yet

Moving notices fully into the hub would mean returning `''` from `wp_admin_notice_markup`. But `capture_notice()` records any notice whose message is non-empty, regardless of its markup, so the title would announce "(3 notices)" while the page shows none. There is no message filter or remove-one-notice method to fix that, and `reset()` clears everything.

**Possible Trac feedback before 7.2 ships:** add a filter to opt a notice out of collection, or skip notices whose filtered markup is empty.

### 4. Optional: match the count

The hub icon could show the same page-notice count that core adds to the title, so the two agree.
