# #616: Fix the database migration gate and add a v1 → v2 upgrade routine

- **URL:** https://github.com/WordPress/wp-feature-notifications/issues/616
- **State:** OPEN
- **Author:** @jonathanbossenger
- **Created:** 2026-10-16T08:36:42Z
- **Labels:** bug, [Scope] Database / Persistence, php

## Description

Part of #302. Depends on #615.

### What problem does this address?

`Activator::create_tables()` only runs its schema when `! $db_version`, which is only true on a fresh install. Any site that activated 0.2.0 has `wp_notifications_db_version = '1'` and stays on v1 forever. It also only runs on the activation hook, and upgrading a plugin doesn't fire activation again.

The `in_array( $table, $wpdb->get_results( 'SHOW TABLES' ), true )` guard compares strings to `stdClass` rows, so it is always false.

### What is your proposed solution?

- Replace the gate with a `version_compare` dispatch, hooked on `plugins_loaded` (priority 5) as well as activation. On multisite, each site upgrades its own tables on its first request, which avoids the `switch_to_blog()` loop that times out on large networks.
- Add a `wp_cache_add()` lock so two concurrent requests don't both run `dbDelta`.
- **v1 → v2: drop and recreate.** `dbDelta` can't drop a column, add a primary key to an existing table, or add `AUTO_INCREMENT`, which together cover every v2 change. Notification data is ephemeral, and the plugin is pre-1.0 with no .org release. Put the destructive path behind `apply_filters( 'wp_notifications_preserve_v1_data', false )` and document it in the `readme.txt` upgrade notice. Use real incremental migrations from v2 onwards.
- Delete the broken `SHOW TABLES` guard (`dbDelta` is idempotent) and drop the `_v1` method suffixes.
- Update `tests/phpunit/tests/test-activator.php`, which calls `create_tables_v1()` directly. Add a migration test: seed `db_version = '1'`, run the upgrade, check with `SHOW COLUMNS` that `channel_title` is gone and `id` is `auto_increment`, and check with `SHOW INDEX` that both primary keys exist.

### @dknauss — 2026-10-16T22:54:03Z

A related activation-only case reproduced during multisite compatibility testing on develop `171f84fe8b21aac0450b19dd1f46bdc63f971b8c` (WordPress 7.1.3 / PHP 8.4.26 / Studio SQLite): **a new site created after network activation receives neither the three notification tables nor `wp_notifications_db_version`.**

Steps on a disposable network:

1. Network-activate WP Feature Notifications. Verify the existing main site has `notifications_messages`, `notifications_subscriptions`, `notifications_queue` under its prefix and DB version `1`.
2. Create a second site through WordPress.
3. Switch to that site and check the three prefixed table names and `get_option('wp_notifications_db_version')`.

Observed: all three child-site tables are absent; DB version is `false`. The same missing state persists with Keel deactivated, so this is not a Keel conflict. Network-deactivating/reactivating Notifications creates all three child tables and version `1`, confirming the same schema can be created by the activation path on this database.

There is no `wp_initialize_site` hook in the tested source. The proposed per-site first-request migration path should cover this case too; please add a new-site-after-network-activation regression test. The current GET endpoint still returns a hard-coded empty list, so an empty successful response does not establish that the child tables exist.

Related multisite design discussion: #64. No production network was changed.
